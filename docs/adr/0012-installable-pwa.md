# 0012 — Installable as a PWA, with a service worker that caches no content

**Status:** Accepted
**Date:** 2026-07-31

## Context

q2 is a phone application that currently runs in a browser. The UI is designed
and tested at 390 × 844, the layout accounts for a notch, and the plan has
always been to package it with Capacitor
([next-steps.md](../next-steps.md) item 15).

Capacitor is not the next step, but the gap between "a website that looks like
an app" and "an app" is smaller than it looks: a web app manifest and a service
worker turn q2 into something that installs from the browser, opens without
browser chrome and sits on a home screen with the others. That is worth having
before the native shell, and it is the same UI either way.

The decision that actually needed making is not *whether* to add a service
worker. It is **what a service worker in q2 is allowed to cache**, and the
answer is not the usual one.

## The constraint that shapes everything

**q2 renders on the server, and every screen is somebody's signed-in one.**

The obvious PWA — precache the shell, serve pages stale-while-revalidate, cache
API responses so the app opens instantly — would put one person's goals, tasks
and chat messages into a cache directory on the device. Those goals can be
health-related ([privacy.md](../privacy.md)), the cache outlives the session
cookie, and a phone is a device other people pick up. Signing out would have to
purge it reliably, from a code path that runs while the network may be down.

That is a data-protection problem dressed up as a performance feature, and it is
not one this version needs to take on: q2 is useless without the API anyway.

## Decision

**q2 is installable, and does not work offline.**

The service worker (`app/service-worker/sw.ts`) does exactly two things:

- **precaches the build output** — the hashed JavaScript and CSS, the fonts, the
  icons, the manifest. Those bytes are identical for every person and their
  names contain a content hash, so a cached copy can never be the wrong version
  of itself and can never be somebody's data;
- **serves an offline page** when a navigation cannot reach the server.

Every navigation is `NetworkOnly`. API requests go to a different origin and no
route matches them, so they are never touched. There is no runtime caching, no
stale-while-revalidate, no background sync.

**`injectManifest`, not `generateSW`.** `@vite-pwa/nuxt` generates the manifest,
builds the worker and substitutes the precache list; the caching rules are
written out as code rather than assembled from Workbox presets, because the
rules *are* the decision here and a preset would hide it.

**No install UI.** Browsers already offer installation in their own menus.
A button in the settings screen would mean new strings, a component, an iOS
special case (Safari has no `beforeinstallprompt`) and a test — for something
the platform does better.

**Auto-update.** The worker calls `skipWaiting()` and `clients.claim()` rather
than waiting for every window to close. q2 is used like an app, so "the update
applies once you have closed all windows" would mean it rarely applies. The
usual objection does not arise here, because the worker serves a running page no
HTML and no data — only content-hashed assets its own document asked for.

## The offline page

It is generated by the worker rather than precached as a file, because it has to
render with the application stopped: no bundle, no design tokens, no fonts.

It takes its words from `app/app/i18n/messages.ts` like everything else, and
picks the language from `navigator.language` — the person's real preference is
stored on their account, which is precisely what cannot be reached at that
moment. German is the fallback.

It names no colour. `Canvas` and `CanvasText` are CSS system colours that follow
the operating system's light or dark setting on their own, which keeps the rule
that [main.css](../../app/app/assets/css/main.css) sets: nothing outside that
file names a hex value. The two exceptions that could not be avoided — the
manifest's `theme_color` and the `theme-color` meta tags, both painted before a
stylesheet exists — are together in `app/app/utils/themeColors.ts`, and main.css
points at it.

## Consequences

**Good**

- q2 installs from Chrome, Edge and Safari, and opens in its own window with the
  status bar coloured to match the theme.
- A cold start on a slow connection paints as soon as the HTML arrives; the
  bundle is already on the device.
- Losing the connection produces a q2 page rather than the browser's error, in
  the person's language.
- Nothing personal is written to the device. Signing out has nothing to purge,
  which is one fewer thing to get wrong in a code path that runs offline.

**Bad, and accepted**

- **q2 does not work offline.** Opening it with no connection gets the offline
  page, not a stale dashboard. This is a deliberate trade and the reason to
  revisit is below.
- A service worker sits between the app and the network on every navigation. It
  passes them straight through, but it is one more thing in the path when
  something looks wrong — the first question for a "stale asset" report is
  whether an old worker is still registered.
- Three dependencies (`@vite-pwa/nuxt` and three `workbox-*` runtime packages)
  where [AGENTS.md](../../AGENTS.md) section 6 asks for none without a
  discussion. This file is that discussion: the alternative was hand-rolling
  precache revisioning and cache lifecycle, which is exactly the kind of code
  worth not owning.

**Neutral**

- The icons in `app/public/` are committed rather than generated at build time.
  They are an input to the build, not a product of it, and the geometry behind
  them is a set of decisions — see `app/scripts/generate-icons.ts`, which
  regenerates the whole set with `bun run app:icons`.

## When to revisit

**When offline use is actually asked for.** Ticking off a task on the train is
a real feature request waiting to happen, and it needs more than a cache: a
write queue, conflict resolution, and an answer for what a stale check-in means
when it arrives an hour late. At that point the caching rule above changes, and
the thing that has to be designed first is not the cache but **what happens on
sign-out** — see [privacy.md](../privacy.md) section 8.

**When Capacitor lands** ([next-steps.md](../next-steps.md) item 15). A native
shell replaces the manifest and the install flow, and the icons here are the
source the native icon sets are generated from. The service worker does not
travel: a Capacitor WebView serves its assets from the bundle already.
